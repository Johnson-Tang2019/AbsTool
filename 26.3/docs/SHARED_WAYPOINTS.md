# Server-shared waypoints (26.3)

In beta.8, each visible color group has a category name. Administrators can use **Rename** beside the group header; names are limited to 32 characters, and a blank name restores the default label. Names are shared by players on that server and survive server restarts. Viewers cannot edit names. A concurrent rename requires reopening the editor against the newer revision. **AbsServerTool 0.3.8 or newer with the category channels is required for naming**; older servers keep normal waypoint support with naming disabled. The optional `absservertool:waypoint_categories_request` and `absservertool:waypoint_categories_snapshot` channels leave the existing protocol-v2 waypoint packets unchanged. The server stores names separately in the world's `data/absservertool_waypoint_categories.json`.

Category controls now use a low-opacity background and border with fully readable text. The in-game Ab's Tool settings backdrop is lighter and has no blur; other game screens retain their own background behavior. A small two-unit server-rack glyph precedes shared waypoint names in Xaero Minimap and World Map. It is only a display prefix; server names and locally saved Xaero waypoints are unchanged. The glyph is supplied as a bitmap font provider, with no additional Xaero version restrictions.

The Shared Waypoints settings category lists every synchronized waypoint below its live connection/permission/count status. Points are grouped by the sixteen protocol colors, with individual color folds, expand/collapse all, and refresh. Open a row to view its complete name, dimension ID, coordinates, symbol, color, and visibility. Read-only players can select/copy field text; administrators can submit edits. Permission loss or a changed/deleted waypoint disables saving immediately. Color changes move to their new groups after the authoritative server update.

Screenshot image clipboard copying is enabled by default in the Optimization settings. The normal PNG is saved first; a background worker prepares PNG/BMP image formats, and Minecraft's main thread publishes them through SDL. Clipboard failures do not prevent the PNG save. Windows receives a native bitmap-compatible format; other platforms are offered PNG first. This requires no external clipboard program or Java AWT desktop clipboard.

Fabric and NeoForge: with compatible Xaero Minimap and World Map interfaces, right-click a local waypoint on the world map and choose **Publish to server**. A shared waypoint offers **Update server waypoint** and **Delete from server** (with confirmation). The existing Minimap waypoint list also retains these actions. Find that list through Minecraft Controls -> Xaero's Minimap -> Waypoints; bindings may be customized.

There is no Xaero version whitelist or upper limit. The current Minecraft 26.3 Fabric Minimap releases 26.5.1–26.6.0 and World Map releases 1.46.2–1.47.0, and NeoForge Minimap releases 26.5.2–26.6.0 and World Map releases 1.46.3–1.47.0, pass the required interface checks. Future releases are inspected before applying the optional integration; changed required interfaces disable it with a log message.

Ab's Tool bindings are listed under Controls -> Key Binds -> Ab's Tool on both loaders. Hold the two settings keys together (R+B by default). Unbind either one to use the other as a single key; unbind both to disable the settings shortcut. The dedicated elytra launch key defaults to unbound and takes effect when the feature is enabled with the key trigger selected. Vanilla persists all of these bindings in `options.txt`.

Enable server-shared waypoints in AbsTool settings. The server must advertise the capability and grant management permission (default OP level 2); a full snapshot must have arrived before writes are enabled. The right-click entries stay disabled for unsupported servers and read-only players. No minimap/map dependency is required on dedicated servers.

The 26.3 client follows AbsServerTool 0.3.6: combined `shared_waypoint_mutation_request` (1 create, 2 update, 3 delete), fixed-width integer colors, 8-character symbols, deltas with a nullable body, mutation dataset revision, and error message text. The internal client delta model remains 0/1/2 after decoding. The 26.2 code and protocol are unchanged.

Verification: `:fabric:verifyWaypoint` and `:neoforge:verifyWaypoint` check independent server-format wire fixtures. Both loaders run `verifyClientUtilities` for image-format round trips, screenshot bytecode hook locations, live groups/folds, and permission-controlled writes. `verifyXaeroParity` compares the shared Xaero, waypoint UI, screenshot and clipboard bytecode in both release JARs and validates their mixin configurations; it is part of the root `build` and release workflow. `:fabric:verifyXaero` and `:neoforge:verifyXaero` inspect real release JARs supplied through `-PxaeroReferenceDir=<reference directory>`.

The optional Fabric menu smoke remains available through `:fabric:runClient -PwaypointMenuSmoke -PxaeroReferenceDir=<26.3 Fabric mods directory>`. Only the two Xaero JARs are loaded; smoke fixtures are excluded from production artifacts. Builds and interface checks do not prove multiplayer mutation persistence or visual behavior on a live NeoForge client.
